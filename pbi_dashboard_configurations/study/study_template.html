How the two columns were produced

Both sides answer the same question for the same periods, and neither was re-implemented for this document — each was read the way it is read in production.

  1. Actual columns. Aggregated straight from v_bidata_live. Value and quantity come from the bi_type = 'S' rows; target from the separate bi_type = 'B' rows. Amount is taken as stored and never re-derived from quantity — the view's output quantity is catalog-gated while its amount is not, so rebuilding value from units would roughly halve every figure.
  2. Dashboard columns. Read from the board's own data route, not from its SQL. The KPI tile values are taken as returned, so what a reader sees on the board is what is tabulated here.
  3. Prior year is the previous year's own actuals recomputed the same way on both sides, not the feed's stored bi_pyamount column — that is how the boards derive it.
  4. Which years. The two most recent the feed carries. A third tab would only repeat what the second tab's prior-year columns already show, and every year here is compared against its own predecessor whether or not that year has a tab of its own.
  5. The cutoff. A part-finished year is reported only as far as the boards carry figures; the months after that are set to zero on both sides in every measure, rather than left partly populated where they would read as a shortfall instead of a month that has not happened. The agreement count below covers only the populated cells.
  6. Match tolerance. Value cells within half a halala (SAR 0.005) count as matching; quantity cells must be exact. A variance too small for two decimals is shown as <0.01% rather than rounded to 0.00%, which would read as agreement.
